# pthread 线程同步原语调用链分析

> 基于 clangd LSP 语义分析 (glibc 2.43.9000, AArch64)

## 概述

本文档分析 glibc NPTL 线程同步原语的完整调用路径：
- **pthread_mutex_lock/unlock** — 互斥锁
- **pthread_cond_wait/signal/broadcast** — 条件变量
- **底层 futex 接口** — 用户态/内核态桥梁

所有同步原语最终归结为 Linux `futex()` 系统调用。

## 1. pthread_mutex_lock 调用链

### 1.1 快速路径: `___pthread_mutex_lock()` [nptl/pthread_mutex_lock.c:70]

```
pthread_mutex_lock(mutex)  → ___pthread_mutex_lock(mutex)
│
├── [快速路径: PTHREAD_MUTEX_NORMAL/DEFAULT]
│   └── lll_mutex_lock_optimized()  [pthread_mutex_lock.c:35]
│       — 原子 CAS: 0→1 (无竞争，立即返回)
│       — 失败→走慢路径
│
├── [自适应自旋: PTHREAD_MUTEX_ADAPTIVE_NP]
│   ├── max_adaptive_count()        [pthreadP.h:44] — 最大自旋次数
│   ├── get_jitter()                [pthread_mutex_backoff.h:22] — 抖动值
│   ├── get_next_backoff()          [pthread_mutex_backoff.h:29] — 退避时间
│   └── [自旋循环: CAS 尝试 max_count 次]
│       → 成功: 返回 0
│       → 超过次数: 进入 futex 等待
│
├── [慢路径: 锁已被持有]
│   └── __lll_lock_wait[_private]() [lowlevellock.c:25/40]
│       └── futex_wait()            [futex-internal.h:124]
│           → ★ futex(FUTEX_WAIT, futex_word, expected)
│           → 内核将线程挂起，直到 futex_word 变化
│
└── [复杂互斥锁类型]
    └── __pthread_mutex_lock_full() [pthread_mutex_lock.c:169]
        — RECURSIVE / ERRORCHECK / PI / PP / ROBUST
```

### 1.2 完整互斥锁: `__pthread_mutex_lock_full()` [nptl/pthread_mutex_lock.c:169]

处理所有非普通类型的互斥锁：

```
__pthread_mutex_lock_full(mutex)
│
├── [PTHREAD_MUTEX_RECURSIVE]
│   — 同一线程重入: count++, 立即返回
│   — 不同线程: futex_wait 等待
│
├── [PTHREAD_MUTEX_ERRORCHECK]
│   — 同一线程重入: 返回 EDEADLK
│   — 不同线程: futex_wait 等待
│
├── [PTHREAD_MUTEX_PI (优先级继承)]
│   ├── __futex_lock_pi64()         [futex-internal.c:145]
│   │   → ★ futex(FUTEX_LOCK_PI, ...)
│   │   → 内核自动进行优先级继承
│   └── [超时版本]
│       └── __futex_abstimed_wait64()  [futex-internal.c:124]
│
├── [PTHREAD_MUTEX_PP (优先级保护)]
│   ├── __pthread_current_priority()  [tpp.c:162]
│   ├── __pthread_tpp_change_priority() [tpp.c:53]
│   │   — 提升当前线程优先级到 mutex 的优先级上限
│   └── futex_wait()                — 竞争时等待
│
├── [PTHREAD_MUTEX_ROBUST]
│   — 持有者死亡检测: EOWNERDEAD
│   — 一致性恢复: pthread_mutex_consistent()
│   └── futex_wait() / futex_unlock_pi()
│
└── __lll_lock_wake[_private]()     [lowlevellock.c:55/62]
    — 错误恢复时唤醒等待者
```

### 1.3 futex 等待底层路径

```
__lll_lock_wait[_private](futex_word)
│
├── [循环: 直到获得锁]
│   ├── atomic_exchange(futex_word, 2)  — 设置为"有等待者"状态
│   └── futex_wait(futex_word, 2, private)
│       └── [内核 futex] — 若 *futex_word==2 则睡眠
│           → 被 futex_wake 唤醒后重试 CAS
│
└── [成功获得锁: *futex_word 从 0/1 → 2]
```

**futex 值语义 (LLL):**
| 值 | 含义 |
|----|------|
| 0 | 锁空闲 |
| 1 | 锁被持有，无等待者 |
| 2 | 锁被持有，有等待者 |

## 2. pthread_mutex_unlock 调用链

### 2.1 入口: `___pthread_mutex_unlock()` [nptl/pthread_mutex_unlock.c:356]

```
pthread_mutex_unlock(mutex) → ___pthread_mutex_unlock(mutex)
│
└── __pthread_mutex_unlock_usercnt(mutex, 1)  [pthread_mutex_unlock.c:47]
    │
    ├── [快速路径: NORMAL mutex, 无等待者]
    │   └── lll_mutex_unlock_optimized()  [pthread_mutex_unlock.c:33]
    │       — atomic_exchange(lock, 0)
    │       — 若旧值 > 1 (有等待者):
    │         → __lll_lock_wake[_private]()  [lowlevellock.c:55/62]
    │           └── futex_wake(futex_word, 1, private)
    │               → ★ futex(FUTEX_WAKE, futex_word, 1)
    │               → 唤醒 1 个等待者
    │
    └── [复杂类型]
        └── __pthread_mutex_unlock_full()  [pthread_mutex_unlock.c:99]
            ├── [RECURSIVE] — count--, 非零则直接返回
            ├── [PI] → futex_unlock_pi()
            │   → ★ futex(FUTEX_UNLOCK_PI, ...)
            │   → 内核选择最高优先级等待者唤醒
            ├── [PP] → __pthread_tpp_change_priority()
            │   — 恢复线程原始优先级
            │   → futex_wake()
            └── [ROBUST] → futex_wake()
```

## 3. pthread_cond_wait 调用链

### 3.1 入口: `___pthread_cond_wait()` [nptl/pthread_cond_wait.c:450]

```
pthread_cond_wait(cond, mutex) → ___pthread_cond_wait(cond, mutex)
│
└── __pthread_cond_wait_common(cond, mutex, NULL)  [pthread_cond_wait.c:330]
```

### 3.2 核心等待: `__pthread_cond_wait_common()` [nptl/pthread_cond_wait.c:330]

glibc 的条件变量使用 **双组 (G1/G2) 轮转算法** 实现公平唤醒：

```
__pthread_cond_wait_common(cond, mutex, abstime)
│
│ ===== 阶段 1: 注册为等待者 =====
│
├── __condvar_fetch_add_wseq_acquire()  [pthread_cond_common.c:38]
│   — 原子递增 wseq (等待序列号)，获取当前组 (G1/G2)
│
├── __condvar_get_private()         [pthread_cond_common.c:184]
│   — 获取进程共享标志 (PRIVATE/SHARED)
│
│ ===== 阶段 2: 释放互斥锁 =====
│
├── __pthread_mutex_unlock_usercnt(mutex, 0)
│   — 释放 mutex，允许其他线程进入临界区
│   — (usercnt=0: 不减少用户引用计数)
│
│ ===== 阶段 3: futex 等待循环 =====
│
├── __pthread_cleanup_push(cleanup)  [cleanup_compat.c:23]
│   — 注册取消清理函数 (支持 pthread_cancel)
│
├── [等待循环]
│   ├── __condvar_load_g1_start_relaxed()  [pthread_cond_common.c:44]
│   │   — 检查是否已被信号唤醒 (g1_start 变化)
│   │
│   ├── __futex_abstimed_wait_cancelable64()  [futex-internal.c:134]
│   │   └── __futex_abstimed_wait_common()   [futex-internal.c:67]
│   │       └── __futex_abstimed_wait_common64()  [futex-internal.c:51]
│   │           └── __internal_syscall_cancel()  [cancellation.c:25]
│   │               → ★ futex(FUTEX_WAIT, &cond->__g_signals[g], 0, timeout)
│   │               → 可被 pthread_cancel 取消
│   │
│   └── [唤醒后: 检查是否真正被 signal/broadcast 唤醒]
│       — 避免虚假唤醒 (spurious wakeup)
│
├── __pthread_cleanup_pop()         [cleanup_compat.c:39]
│
│ ===== 阶段 4: 确认唤醒 =====
│
├── __condvar_confirm_wakeup()      [pthread_cond_wait.c:47]
│   — 原子递减 g_refs (组引用计数)
│
│ ===== 阶段 5: 重新获取互斥锁 =====
│
└── __pthread_mutex_cond_lock(mutex)  [pthread_mutex_cond_lock.c:13]
    — 重新锁定 mutex (可能阻塞)
    — 使用特殊的 cond_lock 版本 (处理 robust 语义)
```

### 3.3 取消处理

```
若在 futex 等待期间收到 pthread_cancel:
  → __condvar_cancel_waiting()      [pthread_cond_wait.c:78]
    ├── __condvar_acquire_lock()    — 获取 condvar 内部锁
    ├── __condvar_load_g1_start_relaxed() — 读取组状态
    ├── [决定是否需要信号其他等待者]
    │   ├── __pthread_cond_broadcast() — 广播唤醒 (补偿消耗的信号)
    │   └── __pthread_cond_signal()    — 单个唤醒
    └── __condvar_release_lock()
```

## 4. pthread_cond_signal / broadcast 调用链

### 4.1 signal: `___pthread_cond_signal()` [nptl/pthread_cond_signal.c:34]

唤醒一个等待者：

```
pthread_cond_signal(cond) → ___pthread_cond_signal(cond)
│
├── __condvar_get_private()         [pthread_cond_common.c:184]
├── __condvar_acquire_lock()        [pthread_cond_common.c:114]
│   — 获取 condvar 内部自旋锁 (__lock 字段)
│
├── __condvar_load_wseq_relaxed()   [pthread_cond_common.c:32]
│   — 读取当前等待序列号
│
├── [检查是否有等待者]
│   — 无等待者: 直接返回
│
├── __condvar_switch_g1()           [pthread_cond_common.c:200] — 可能切换组
│   ├── __condvar_get_orig_size()   — 当前组大小
│   ├── __condvar_load_g1_start_relaxed() — 组起始序号
│   ├── __condvar_add_g1_start_relaxed() — 推进 g1_start
│   ├── __condvar_fetch_xor_wseq_release() — 切换当前组 bit
│   └── __condvar_set_orig_size()   — 重置组大小
│
├── [递增 __g_signals[g] 信号计数]
│
├── __condvar_release_lock()        [pthread_cond_common.c:149]
│   — 释放 condvar 内部自旋锁
│
└── futex_wake(&cond->__g_signals[g], 1, private)
    → ★ futex(FUTEX_WAKE, &__g_signals[g], 1)
    → 唤醒 1 个等待在该组的线程
```

### 4.2 broadcast: `___pthread_cond_broadcast()` [nptl/pthread_cond_broadcast.c:38]

唤醒所有等待者：

```
pthread_cond_broadcast(cond) → ___pthread_cond_broadcast(cond)
│
├── __condvar_get_private()
├── __condvar_acquire_lock()
├── __condvar_load_wseq_relaxed()
│
├── [G2 组不为空时]
│   └── futex_wake(&__g_signals[g2], INT_MAX, private)
│       → 唤醒 G2 组所有等待者
│
├── __condvar_switch_g1()           — 切换 G1/G2
│   — 将所有 G1 等待者移入新的可唤醒队列
│
├── __condvar_release_lock()
│
└── futex_wake(&__g_signals[new_g2], INT_MAX, private)
    → 唤醒新 G2 组所有等待者
```

## 5. 条件变量双组轮转算法

### 5.1 数据结构

```c
struct pthread_cond_t {
    __wseq;          // 等待序列号 (低1位=当前组标记)
    __g1_start;      // G1 组起始序列号
    __g_refs[2];     // 每组引用计数 (活跃等待者)
    __g_signals[2];  // 每组信号计数 (futex 等待字)
    __g_size[2];     // 每组大小
    __g1_orig_size;  // G1 原始大小 (用于切换判断)
    __lock;          // 内部自旋锁
};
```

### 5.2 组切换逻辑

```
初始状态: G1=空, G2=空, 当前组=G1

等待者 A 进入: wseq 低位=0 → 加入 G1
等待者 B 进入: wseq 低位=0 → 加入 G1

signal() 到来:
  1. G1 有等待者 → 信号 G1
  2. G1 全部消耗 → 切换: 旧G2→新G1, 新等待者→新G2
     __condvar_switch_g1():
       g1_start += orig_size  (推进)
       wseq ^= 1              (翻转当前组位)
       orig_size = 新G1大小

这保证:
  - 先等待的先被唤醒 (FIFO 公平性)
  - signal 不会丢失
  - broadcast 能唤醒所有
```

## 6. 底层 futex 接口

### 6.1 futex 调用路径

```
glibc 用户态
├── futex_wait(word, expected, private)  [futex-internal.h:124]
│   └── 内联: syscall(SYS_futex, word, FUTEX_WAIT|private, expected, NULL)
│       — 若 *word == expected: 线程休眠
│       — 若 *word != expected: 立即返回 EAGAIN
│
├── futex_wake(word, count, private)     [futex-internal.h:187]
│   └── 内联: syscall(SYS_futex, word, FUTEX_WAKE|private, count)
│       — 唤醒最多 count 个等待者
│
├── __futex_abstimed_wait64()            [futex-internal.c:124]
│   └── __futex_abstimed_wait_common()   [futex-internal.c:67]
│       └── __futex_abstimed_wait_common64()  [futex-internal.c:51]
│           └── __internal_syscall_cancel()  [cancellation.c:25]
│               → futex(FUTEX_WAIT, word, expected, &timeout)
│               → 支持超时 + 线程取消
│
├── __futex_lock_pi64()                  [futex-internal.c:145]
│   → futex(FUTEX_LOCK_PI, word, ...)
│   → 内核管理优先级继承链
│
└── futex_unlock_pi()                    [futex-internal.h:243]
    → futex(FUTEX_UNLOCK_PI, word)
    → 内核选择最高优先级等待者
```

### 6.2 FUTEX_PRIVATE_FLAG

```
private = FUTEX_PRIVATE_FLAG (进程内):
  — 内核优化: 不需要共享页表查找
  — 性能提升约 30%
  — 仅限同一进程内的线程

private = 0 (进程间共享):
  — 需要通过物理页面地址匹配
  — 用于 PTHREAD_PROCESS_SHARED 属性的同步原语
```

## 7. 自适应互斥锁详解

### 7.1 自旋策略: `___pthread_mutex_lock()` 中的自适应逻辑

```
[PTHREAD_MUTEX_ADAPTIVE_NP 类型]:

max_count = max_adaptive_count()  — tunable: glibc.pthread.mutex_spin_count
jitter = get_jitter()             — 基于 ADRP 的随机化

for (cnt = 0; cnt < max_count; cnt++) {
    if (CAS(lock, 0, 1) == 0)
        return 0;  // 获得锁！
    
    // 退避
    backoff = get_next_backoff(cnt)
    pause(backoff)  // 或 YIELD
}

// 自旋失败，进入 futex 等待
__lll_lock_wait(lock)
```

**设计目的：**
- 短临界区：自旋避免上下文切换开销
- 长临界区：超时后 futex 休眠节省 CPU
- 退避 + 抖动：减少缓存行争用

## 8. 完整交互时序

### 8.1 mutex lock + cond_wait + signal

```
线程 A (生产者)                    线程 B (消费者)
────────────────                   ────────────────
pthread_mutex_lock(mtx)
  → CAS(0→1) 成功
                                   pthread_mutex_lock(mtx)
                                     → CAS 失败
                                     → __lll_lock_wait()
                                       → futex_wait(mtx, 2)
                                       → [内核挂起线程B]

[生产数据]

pthread_mutex_unlock(mtx)
  → exchange(lock, 0)
  → 旧值=2 (有等待者)
  → futex_wake(mtx, 1)
  → [内核唤醒线程B]
                                     → [线程B被唤醒, CAS(0→2)]
                                     → 获得锁
                                   
                                   pthread_cond_wait(cond, mtx)
                                     → wseq++ (注册为G1等待者)
                                     → unlock(mtx, usercnt=0)
                                       → futex_wake(mtx, 1) [如有等待者]
                                     → futex_wait(&g_signals[g], 0)
                                     → [内核挂起线程B]

pthread_mutex_lock(mtx)
  → CAS(0→1) 成功

[再次生产数据]

pthread_cond_signal(cond)
  → acquire_lock(cond)
  → g_signals[g]++
  → release_lock(cond)
  → futex_wake(&g_signals[g], 1)
  → [内核唤醒线程B]
                                     → [线程B被唤醒]
                                     → confirm_wakeup()
                                     → __pthread_mutex_cond_lock(mtx)
                                       → [等待线程A释放锁]

pthread_mutex_unlock(mtx)
  → futex_wake(mtx, 1)
                                     → [获得锁, cond_wait返回]
                                     → [消费数据]
```
